# Contract: Output state directory and ownership manifest

**Feature**: `022-v151-fix-batch` | **Status**: normative (amends
[014 output-layout.md](../../014-viewmodel-renderers/contracts/output-layout.md))

## State directory

The build keeps its ownership manifest outside the output directory.

```
<project root>/
├── dist/                       # output directory: only generated artifacts, no dot-files
└── .dist.loko/                 # state directory: tool state for this output directory
    └── manifest                # the paths the last build owns, sorted
```

- Name: `.<base>.loko`, where `<base>` is the output directory's own base name.
  `--out release` → `.release.loko`. Never created inside the output directory.
- Created lazily on first write (`0755`); holds one file, `manifest` (`0644`).
- One state directory per output directory. Sibling projects never collide, because
  the state directory is resolved relative to its output directory's parent.
- Deployments that copy or publish the output directory do not carry tool state.
- Confinement: an MCP build (`Store.Confine`) refuses an output directory that
  resolves to the project root. Its state directory would be the root's sibling,
  outside the project. A CLI `--out` stays unconfined, as in 1.5.0.
- The manifest is written atomically: a temporary file in the state directory,
  then a rename onto `manifest`.

## Manifest file

Contents are unchanged from 1.5.0:

- Line 1: `# Code generated by loko from <sources>. DO NOT EDIT.` with `<sources>`
  the sorted, `, `-joined list of project-relative `*.loko.hcl` files.
- Then one owned path per line, output-relative, forward slashes, sorted.
- Decoding drops comment lines, blank lines and every path that is absolute or
  escapes the output root; a corrupt manifest can only narrow pruning.

## Read and write rules

1. The build reads the state manifest
   (`<parent(outDir)>/.<base>.loko/manifest`).
2. A state manifest that is missing, unreadable or corrupt yields an empty
   manifest; the build then prunes nothing.
3. **Legacy fallback**: when the state manifest is absent, a 1.5.0-level
   `.loko-manifest` inside the output directory is read instead.
4. The build writes the state manifest for the new artifact set after artifacts
   are written and pruning has run.
5. **Legacy retirement**: after the state manifest is in place, a surviving legacy
   `.loko-manifest` inside the output directory is removed. A build that fails at
   any earlier step of `Commit` leaves the legacy file untouched; the next run
   re-reads it and retries.
6. Artifact paths that are unsafe, or that collide with the manifest's own name,
   are refused before any write (unchanged from 1.5.0).

## Determinism

- Same project + same artifact set → same manifest bytes, byte for byte.
- The manifest is not part of the published site: it carries no timestamp, host,
  tool version or absolute path, and it lives outside `dist/`.
